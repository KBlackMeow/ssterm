# Agent 自适应上下文压缩阈值设计

## 目标

以 token 预算而非消息数量决定 Agent 历史压缩时机，在已知模型上尽量接近上下文窗口才压缩，同时让未知窗口的自定义模型和 Ollama 保持安全。

## 问题

当前实现固定在 20 个历史项后压缩。工具调用与结果会迅速消耗这些项，而短消息与 8KB 工具反馈权重相同，导致通常仅数次工具循环就摘要。

## 预算模型

每个模型配置新增可选 contextWindowTokens。内置云模型提供已知窗口；未填写的自定义模型及 Ollama 以 32,000 tokens 作为保守窗口。

上下文使用量优先使用 API 响应返回的 input、cache 和 output token 之和；没有 usage 的 provider 才使用本地保守估算。估算包含系统提示词、技能目录、会话上下文、历史消息与工具结果。

计算规则：

- 摘要输出预留为 min(模型最大输出上限, 16,000)，且至少 4,000。
- 已知窗口的自动压缩点为 contextWindowTokens - summaryReserve - 12,000。
- 未知 32K 窗口的自动压缩点固定为 16,000。
- 达到窗口的 90% 或 provider 报告上下文过长时，强制压缩并将原始请求重试一次。
- 80 个历史项仅作为无 token usage 的异常兜底，不作为日常压缩条件。

典型数值：

| 上下文窗口 | 摘要预留 | 自动压缩点 |
|---:|---:|---:|
| 未知 / 32K | 4K | 16K |
| 64K | 12K | 40K |
| 128K | 16K | 100K |
| 200K | 16K | 172K |

## 生命周期

压缩仍保留初始目标、一个最新摘要和完整的近期消息组；工具调用与工具结果不可拆开。压缩失败时使用既有组感知裁剪。上下文过长的重试最多一次，第二次失败将错误呈现给用户，不进入循环。

## 兼容性

现有配置 JSON 缺少 contextWindowTokens 时保持兼容。SSH、终端执行、Agent1/Agent2 的命令执行策略不受影响；仅 Agent 对话历史调度和模型配置发生变化。

## 测试

- 已知窗口按公式给出压缩点。
- 未知模型使用 32K/16K 保守默认。
- API usage 优先于本地估算。
- 80 项兜底不会在 token 预算充足时影响有 usage 的模型。
- 上下文过长只触发一次压缩与重试。
- 旧配置 JSON 可正常加载。
